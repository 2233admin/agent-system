# Skill 组鉴别

判定一个组的去留与归属，并让下一次复核比这一次便宜。只产出判定和证据；执行由别的承载面负责。

## 进入与不进入

进入：手上有候选组要决定收不收；怀疑候选与现有组重复；需要判断某个组服务哪些事项；或某个已收组到了复核节拍。候选可来自外部仓库、marketplace、他人交付或本仓历史资产。

不进入：从零设计新 Skill（`agent-skill-design`）；已决定收下后的改造、拆分、迁移、退役（`skill-maintenance`）；只需要外部标准、版本或客户端兼容性事实（`capability-lifecycle`）；对象是 knowledge 而非 Skill（`knowledge-maintenance`）。

**判定单位是组，不是单个 Skill。** 拿到一个孤立的 Skill 时，先定它属于哪个组；定不出组就先定组边界，不得跳过这一步直接判定单个 Skill——那会把成员从组里拆出来，而组内通常互相调用。

候选存在、已被安装、来源流行或作者可信，都不构成收下的理由。未读过组内正文不得给出判定；只读 README 或 description 不算读过。成员很多时读到能回答全部五门为止，并写明读了哪些、没读哪些。

## 首次判定：五道门

五门顺序执行，任一不过即停止，返回不通过的门与缺口，不继续后面的门。

### 门 1 · 组边界

写出候选组的成员清单，以及成员之间的引用、路由与转发关系。存在互相调用即不得按成员拆分——拆组会拆断。

拆不开又跨越互斥职责的候选，只有两种合法结论：它本来就是一个大方法包（记录它跨哪些事项，进门 2），或者它耦合过度不该收。不得为了让它"归类干净"而先拆再判。

### 门 2 · 事项归属

写出候选组服务的事项，可以多个。指不到任何已存在事项时只有两种合法结论：这是一个**新事项**，需负责人裁决后才继续；或者候选不该存在。不得用「通用」「都能用」「以后可能有用」充当归属。

同时写出该事项当前已有哪些组——门 3 要用。

### 门 3 · 净增量

列出候选组在目标事项内、以及跨事项的最近邻组，逐个说明差异。三种结局：

- **真空缺**：无最近邻覆盖该决定，进入门 4。
- **部分重叠**：必须给出并存之外的处置——收候选并退役旧组，或改造旧组而不收候选。**不得让两个组覆盖同一个决定。**
- **完全重叠**：不收，返回已覆盖它的组。

差异必须用「它替谁做了哪个决定」表述，不得用篇幅、成员数、结构、写法或新鲜度充当净增量。

**本门同样适用于往已收的外来组里加东西**：加之前先查同一个组内是否已有该能力，查不到才加。往组里塞重复能力与收下一个重复组是同一类错误，且更难被发现。

### 门 4 · 路由

`description` 是唯一路由面，按它单独判定，不参考正文补足。对组内**每个**成员检查是否同时写明：正向触发、不适用边界、与相邻 Skill 的职责分界。三者缺一即该成员不通过；组内有成员不通过则整组不通过。

误触发的成本高于漏触发：一个在错误时机加载的 Skill 是负资产。写不出「什么时候不该用我」的候选直接不收，不得由鉴别方替它补写后再判定通过——补写是收下之后 `skill-maintenance` 的工作。

同时检查正文是否越过 `description` 声明的边界，以及是否在正文里安置了第二个控制器、生命周期驱动者或状态库。

### 门 5 · 来源、移植与预算

**来源三分，判据是允不允许本地改动**：`own` 自写；`fork` 拿来直接用并承诺零改动；`vendor` 拿来但打了补丁。

判定 `fork` 时必须给出可机械验证的依据：上游位置、pin 到的 ref、以及一条能重跑的比对步骤。给不出就不能记 `fork`，记 `vendor` 或标未知；**不允许名义 fork、实际改过**——那种改动下次升级一定丢失且无人知晓。判 `vendor` 时逐条登记改动，每条写明升级后如何重打或推回上游。

逐条列出候选组隐含假设的前提，至少覆盖：目录结构与文件路径、依赖的 CLI 或工具及其版本、权限与授权模型、目标客户端与 provider、语言与运行时、它假定存在的其他组或 prompt。每条标记本仓成立、不成立或未知。**未知不得记为成立。** 存在不成立或未知的前提时，结论只能是「改造后收」或「不收」；不得以「先收下再说」「运行时再看」通过本门。

给出候选组的成员数、`description` 字节、主合同字节、按需 references 字节，以及收下后事项与总量的变化。**新增默认伴随抵消**：指出被压缩、合并或退役的对象。给不出抵消时，把「需要提高上限」作为一项负责人裁决返回，不得自行通过；不得用搬运 reference、拆分组、改动承载路径洗白增量——**换个目录不减少任何运行成本，只是让门失效**。

## 复核：不是重判

已收组到节拍时走本节，不重跑五门。

1. 取上次判定留下的**失效条件**与**下次最少复核步骤**，先按最少步骤确认结论是否仍成立。
2. 只重跑被失效条件命中的那道门；其余门沿用上次结论，并注明沿用来源与上次判定时间。
3. 沿用依据本身已失效、或最少复核步骤跑不通时，才退回完整五门重判，并写明为什么退回。
4. 复核后刷新上次复核时间；结论有变的，同时更新失效条件与最少复核步骤。

**外来组的失效条件挂在组上，不挂在成员上**：上游发布新版是全组共享的唯一失效条件，写一次，不是逐个成员写。

无法用最少步骤确认的结论立即退出当前认知，重新核验前只能作历史证据，不得因为已经写下就继续引用。

## 返回

- **判定**：收 / 改造后收 / 不收 / 需负责人裁决；附不通过的门。首次判定与复核要标明是哪一种。
- **组边界**：成员清单与内部引用关系；跨事项时说明为什么不拆。
- **归属**：服务的事项，可多个。
- **处置**：被替代或需同步退役的组；无则明确写无。
- **来源**：`own` / `fork` / `vendor`，附上游位置、ref、许可证、逐条本地改动与更新触发。
- **触发分类**：`new-scenario` 出现新事项／`known-insufficiency` 已知能力不足／`bad-case` 已发生的失败，三选一。
- **证据**：读过的正文范围、未读部分、仍未知的边界。
- **预算**：字节与数量变化及抵消，或待裁决的上限提高。
- **失效条件**：这个判定在什么情况下不再成立。
- **下次最少复核步骤**：怎么用最小代价确认它还成立。

**最后两项不可省。** 不写它们的判定等于制造一个下次必须从零重做的负担，本 Skill 的全部价值就在于消除那个负担。

判定不授权安装、写入配置或修改 profile。「收」交给装配路径执行，「改造后收」交给 `skill-maintenance`，「需负责人裁决」停在此处等待。返回后退出，不代为决定事项的存废。
