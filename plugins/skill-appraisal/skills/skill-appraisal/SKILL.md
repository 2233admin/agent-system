# Skill 组鉴别

判定一个组的去留与归属，并让下一次复核比这一次便宜。只产出判定和证据；执行由别的承载面负责。

## 进入与不进入

三种进入，先判定是哪一种，走的路径不同：

| 进入 | 触发 | 路径 |
| --- | --- | --- |
| **首次判定** | 手上有候选组，要决定收不收 | 门 0 → 门 1–4 全跑 |
| **补判** | 组早已在用，但从未被判定过——没有失效条件、没有复核依据 | 门 0 → 门 1–4 全跑，处置受"它已在用"约束 |
| **复核** | 已判定过的组到了节拍，或失效条件命中 | 只重跑被命中的门，见「复核」一节 |

**补判是现实里最常见的一种，不要当成首次判定。** 差别在处置：首次判定可以简单地"不收"，补判不能——它已经在装配里，正在被使用，还可能有别的组依赖它。补判的合法结论只有：维持、改造、改装配声明、退役并迁移调用者。**「不收」对补判不是合法结论。**

不进入：从零设计新 Skill（`agent-skill-design`）；已定下后的改造、拆分、迁移、退役（`skill-maintenance`）；只需要外部标准、版本或客户端兼容性事实（`capability-lifecycle`）；对象是 knowledge 而非 Skill（`knowledge-maintenance`）。

**判定单位是组，不是单个 Skill。** 拿到孤立的 Skill 时先定它属于哪个组；定不出组就先定组边界，不得跳过这一步直接判定单个 Skill——那会把成员从组里拆出来，而组内通常互相调用。

候选存在、已被安装、来源流行或作者可信，都不构成留下的理由。未读过组内正文不得给出判定；只读 README 或 description 不算读过。成员很多时读到能回答全部门为止，并写明读了哪些、没读哪些。

## 门 0 · 来源与可改动性

**先于其余各门。** 不知道一个组能不能改，就说不清后面任何一门的处置空间——判定完才发现改不了，等于白判。

**来源三分，判据是允不允许本地改动**：`own` 自写，可改；`fork` 拿来直接用并承诺零改动，**不可改**；`vendor` 拿来但打了补丁，改动须逐条登记且升级时要重打。

判 `fork` 必须给出可机械验证的依据：上游位置、pin 到的 ref、一条能重跑的比对步骤。给不出就不能记 `fork`，记 `vendor` 或标未知；**不允许名义 fork、实际改过**——那种改动下次升级一定丢失且无人知晓。

同时记下该组是否依赖外部工具版本。来源类型与外部依赖是两回事：一个 `own` 组也可以锁在某个外部 CLI 版本上，那是它的失效条件之一。

**本门的产出直接约束后面各门的处置**：`fork` 组的任何问题都不能靠改它的正文解决，只能靠装配声明、外置或退役。

## 门 1 · 组边界

写出候选组的成员清单，以及成员之间的引用、路由与转发关系。存在互相调用即不得按成员拆分——拆组会拆断。

拆不开又跨越互斥职责的候选，只有两种合法结论：它本来就是一个大方法包（记录它跨哪些事项，进门 2），或者它耦合过度不该收。不得为了让它"归类干净"而先拆再判。

## 门 2 · 事项归属

写出候选组服务的事项，可以多个。指不到任何已存在事项时只有两种合法结论：这是一个**新事项**，需负责人裁决后才继续；或者候选不该存在。不得用「通用」「都能用」「以后可能有用」充当归属。

同时写出该事项当前已有哪些组——门 3 要用。

## 门 3 · 重叠与净增量

列出候选组在目标事项内、以及跨事项的最近邻组，逐个说明差异。差异必须用「**它替谁做了哪个决定**」表述，不得用篇幅、成员数、结构、写法或新鲜度充当净增量。

三种结局：

- **真空缺**：无最近邻覆盖该决定，进入门 4。
- **完全重叠**：不收（首次判定）或退役并迁移调用者（补判），返回已覆盖它的组。
- **部分重叠**：先分清是哪一种，两者处置完全不同——

  - **同层重叠**：两个组替同一个人做**同一个**决定。不得并存，必须退役其一或改造其一。
  - **跨层重叠**：一个决定「用不用、什么时候停」，另一个决定「具体怎么做」。**这不是冗余，是分层**；正确处置是把分界写进双方的 `description` 与正文，不是退役。判错这一点会砍掉本该配合的能力。

**本门同样适用于往已有的组里加东西**：加之前先查同一个组内是否已有该能力，查不到才加。往组里塞重复能力与收下一个重复组是同一类错误，且更难被发现。

## 门 4 · 路由

`description` 是唯一路由面，按它单独判定，不参考正文补足。对组内**每个**成员检查是否同时写明：正向触发、不适用边界、与相邻 Skill 的职责分界。三者缺一即该成员不通过；组内有成员不通过则整组不通过。

误触发的成本高于漏触发：一个在错误时机加载的 Skill 是负资产。写不出「什么时候不该用我」的候选直接不收，不得由鉴别方替它补写后再判定通过——补写是定下之后 `skill-maintenance` 的工作。

同时检查正文是否越过 `description` 声明的边界，以及是否在正文里安置了第二个控制器、生命周期驱动者或状态库。

## 处置：优先落在装配层

**装配是绝对权威**：每个装配显式声明它要哪些 Skill，没声明的就不存在。这是白名单，不是黑名单——黑名单只排除已知的坏的，上游下次新增就自动漏进来。

由此得出处置的优先顺序：

1. **改装配声明**——两个组各自都合理、只是不该同时出现在同一个装配里时，让该装配只声明其中一个。**这是首选**：不改任何正文，不动 `fork`，也不废掉另一个装配里的合法用法。
2. **补边界**——把分界写进 `own` 组的 `description` 与正文。只能改 `own`；`fork` 不可改。
3. **改造后收 / 迁移**——交给 `skill-maintenance`。
4. **退役**——最后手段。**退役会把所有装配里的它一起废掉**，跨装配影响必须先写清。

**不要因为资产面上有重叠就退役。** 资产面登记的是仓库里有什么，装配面决定的是某次运行里有什么；重叠只有在**同一个装配内**同时出现才是问题。

## 复核：不是重判

已判定过的组到节拍时走本节，不重跑各门。

1. 取上次判定留下的**失效条件**与**下次最少复核步骤**，先按最少步骤确认结论是否仍成立。
2. 只重跑被失效条件命中的那道门；其余门沿用上次结论，并注明沿用来源与上次判定时间。
3. 沿用依据本身已失效、或最少复核步骤跑不通时，才退回完整重判，并写明为什么退回。
4. 复核后刷新上次复核时间；结论有变的，同时更新失效条件与最少复核步骤。

**外来组的失效条件挂在组上，不挂在成员上**：上游发布新版是全组共享的唯一失效条件，写一次，不是逐个成员写。

无法用最少步骤确认的结论立即退出当前认知，重新核验前只能作历史证据，不得因为已经写下就继续引用。

## 预算

给出候选组的成员数、`description` 字节、主合同字节、按需 references 字节，以及变化量。

新增默认伴随抵消：指出被压缩、合并或退役的对象。给不出抵消时，把「需要提高上限」作为一项负责人裁决返回，不得自行通过；不得用搬运 reference、拆分组、改动承载路径洗白增量——**换个目录不减少任何运行成本，只是让门失效**。

**按资产数量设的上限拦不到运行成本**，因为资产数量不等于装配数量。真正按运行成本计的是每项 `description` 的可见字节预算，它逐项生效且与资产总数无关。

## 返回

- **进入类型**：首次判定 / 补判 / 复核。
- **判定**：维持 / 收 / 改造后收 / 改装配声明 / 退役 / 不收 / 需负责人裁决；附不通过的门。补判不得返回「不收」。
- **来源**：`own` / `fork` / `vendor`，附上游位置、ref、许可证、逐条本地改动、更新触发与外部依赖版本。
- **组边界**：成员清单与内部引用关系；跨事项时说明为什么不拆。
- **归属**：服务的事项，可多个。
- **重叠**：最近邻组、是同层还是跨层、以及依据。
- **处置**：按装配层优先的顺序给出；涉及退役时写清跨装配影响。
- **触发分类**：`new-scenario` 出现新事项／`known-insufficiency` 已知能力不足／`bad-case` 已发生的失败，三选一。
- **证据**：读过的正文范围、未读部分、仍未知的边界。
- **预算**：字节与数量变化及抵消，或待裁决的上限提高。
- **失效条件**：这个判定在什么情况下不再成立。
- **下次最少复核步骤**：怎么用最小代价确认它还成立。

**最后两项不可省。** 不写它们的判定等于制造一个下次必须从零重做的负担，本 Skill 的全部价值就在于消除那个负担。

判定不授权安装、写入配置或修改 profile。「改装配声明」交给装配路径执行，「改造后收」与「退役」交给 `skill-maintenance`，「需负责人裁决」停在此处等待。返回后退出，不代为决定事项的存废。
