# Reviewer: adversarial（构造两个都遵守全部 AD、却仍然互不兼容的下层单元）— AD-22

**Verdict: PASS with findings**（1 项 critical）

## F1 [critical] `sourceRef` 的可移植性语义从未被任何 AD 固定，而 AD-22 让它变成真问题

**构造：**

- **单元 A**——实现 #173 的供给能力（AD-22 退役第 (1) 步）。它要把「一批磁盘上的 Skill 目录」变成一条 `configs` 修订。它读 AD-22「字节由 pin 对应的安装器在每台机器上复现」，合理推断修订必须能跨机器使用，于是把 `sourceRef` 写成**仓库相对路径**或某种符号引用。
- **单元 B**——实现 Codex 或任何第二个 client adapter 的内容物化。它读 AD-21「把其 `sourceRef` 解析为真实内容」，并照既有 `content-materializer.ts` 的先例（`resolveSourcePath` 直接返回 `sourceRef.value` 交给 `cp`），把 `sourceRef` 当作**可直接使用的绝对路径**。

两者都逐字遵守了 AD-19、AD-21、AD-22，却对同一个字段给出不兼容的语义。A 产出的修订在 B 手里解析失败，按 AD-10 fail-closed 全部降级为 `unsupported`——而且是静默符合规则地失败，没有任何门会指出根因。

**为什么是 AD-22 让它变成 critical：** 在 AD-22 之前，字节随仓库走，绝对路径与仓库路径事实上一一对应，语义歧义不产生后果。AD-22 明确规定第三方组的字节**不再随仓库走、由每台机器各自复现**——那么同一条修订在两台机器上对应的绝对路径必然不同。可移植性从「无所谓」变成「必须定义」，而 AD-22 恰恰没定义它。

现有证据表明歧义已经真实存在：AD-21 的「阻塞前提」段落要求 Story 4.5b 让 `cap-fs.ts` 把「已知的真实磁盘路径」写入 `sourceRef`——即当前实现方向是绝对路径；而 AD-22 的每机复现要求与之直接冲突。

**处置：** autofix —— 在 AD-22 中把「修订的跨机器可移植性」显式列为退役第 (1) 步必须解决的前提，并点明它必须与 AD-21 的 `sourceRef` 解析语义一并裁定，不得由两个实现者各自选择。不在本条预先裁定选哪种（那需要 #173 落地时的真实证据），但必须禁止「各自发明」。
