- (constraint) clean-slate：现有 Python CAP 仅可作为 Bad Case 证据，不是需求、架构或迁移基线。
- (constraint) MVP 只支持 OMP Agent 单客户端；不得为未承诺的多客户端能力预置进程协议。
- (constraint) 稳定配置只引用 Instructions、Skills、MCP 与任务期输入入口，不复制任务内容或私域原文。
- (constraint) 系统必须区分期望装配、最终结果、运行观察与 Unknown；提供三层验证与跨 Session 可追溯；普通路径最多一次激活确认。
- (decision) 采用 TypeScript 原生 OMP 插件，领域内核保持纯 TypeScript 并通过 ports 与 OMP 适配器隔离；绑定全部 MVP 能力，防止为单客户端 MVP 引入 IPC、重复类型映射和双进程生命周期。
- (direction) 已比较 TypeScript 原生插件、Go/Rust/Python 独立 CLI 加 TypeScript 适配和纯离线配置编译器；独立 CLI 的隔离收益不足以覆盖单客户端 MVP 的协议与分发成本，纯离线方案无法满足运行观察闭环。
- (decision) 采用 Bun 内置 SQLite 作为本机稳定配置修订、激活、差异、观察、验证证据与替代链的唯一持久权威；可读 JSON/Markdown 仅为可重建投影，禁止反向写入或成为第二权威。该决定绑定 FR-3~14，防止跨文件部分提交、并发漂移和跨 Session 丢失。
- (decision) 每次激活是 session-scoped 单元，绑定不可变稳定配置修订、输入引用与指纹、客户端环境证据；运行观察只追加证据，不能反写期望状态，跨 Session 只续接持久事实而不继承旧授权或动态任务状态。
- (decision) 采用六边形模块化单体：domain 不依赖 OMP、SQLite、文件系统或时钟；application commands 是唯一状态变更入口；OMP、SQLite、投影、时钟与指纹为 adapters，依赖方向只向内；同一 Bun 进程部署，不引入服务或 IPC。
- (decision) 单个原生 OMP 扩展提供三类表面：用户命令仅做选择/一次确认/检查，LLM 类型化工具仅做低频配置修订与证据记录，生命周期钩子只读采集观察；三者统一调用 application，禁止直接访问 SQLite。
- (decision) 激活状态机固定为 prepare→confirm-once→apply→observe/reconcile；必需能力、必需输入、实质变化裁决或证据完整性缺失时 fail closed；仅可选项缺失可 degraded，且必须列出差异、Unknown 与受影响能力。
- (decision) SQLite 事务与 OMP 外部副作用不宣称原子：每次操作使用幂等 operation id，副作用后保存可观察结果；失败记录部分结果与差异，重试先 reconcile，禁止以推测回滚冒充成功。
- (decision) Truth 使用显式 Known(value,evidence) 或 Unknown(reason,observedAt) tagged union；null/false 不表达未知。三层验证分别保存，只有三层均有直接证据且通过才可派生 Verified。
- (decision) SQLite 使用 strict tables、WAL、单写者序列化、乐观修订条件和事务迁移；可读投影采用 allowlist，私域原文、凭据和动态任务内容不得持久化或写入日志。
