# Agent Context Assembly 产品简报

## 执行摘要

Agent Context Assembly 面向长期借助 Agent 完成多类真实工作的个人实践者。它把散落、重复、质量不一的 **Instructions、Skills、MCP** 组合成稳定、可复用、可重复激活且可检查的工作配置，使用户不必在每次任务开始时重新研究“该带什么能力、哪些配置真的生效”，而能把主要精力用于完成和验收工作。

产品包含两个节奏不同的工作面：

- **低频 Context Assembly**：仅在新场景、已知不足或真实 bad case 出现时，建模、维护和验证稳定配置；
- **高频 Profile Activation / Context Loading / Task Execution**：普通任务复用已验证配置，经声明入口加载现场背景，执行并验收实际工作。

价值不是“把配置管得更多”，而是以更少的装配干预获得更可靠的任务结果：能力刚好合适，来源、差异、冲突和未知可见，失败能低成本转化为改进。公开 `agent-system` 仓库承载可公开复用部分；个人私有资产和上下文保持独立边界，但仍可在其授权环境中参与装配。产品不是只能处理公开资产的公共目录。

**[推荐] 下一阶段**：选择少量“频率较高、验收结果清楚、对能力组合确有差异”的真实工作样本，建立现状基线并识别首批稳定配置候选；再进入 PRD。届时 Agent 先给出少量候选，负责人只需确认“先验证哪些任务”和“什么结果算完成”，无需从零枚举。

## 问题与机会

个人 Agent 资产分布在不同位置、产品和作用域中，造成重复与质量差异，且安装、发现、许可、本次激活与运行时生效常被混同。结果是 Instructions 冲突、Skills 未触发、MCP 已配置但未连接或未批准；用户每次任务都重新选择方法和能力；关键决定留在历史对话；失败只产生临时修补。

已有事实支持该问题：

- 当前公开仓库已经区分声明态、配置态和生效态，并明确“文件存在或 lock 通过，不等于客户端已经原生加载”。[1]
- 本次工作现场运行 `uv run cap profiles` 时，新增的 `.agents/skills` 被现有门禁识别为 capability bypass 并拒绝继续。这是安装态、声明闭包与可用性不一致的真实 bad case。现有 Python CAP 仅作为问题和概念证据，不作为后续实现基线。
- Claude Code 与 OpenAI Codex 官方文档分别定义 Instructions、Skills、MCP 的多级来源、覆盖或并列、按需加载、启用、批准、连接与调用状态；两者都说明“存在”不能推出“本次生效”。[2][3][4][5][6]
- MCP 服务器可暴露 prompts、resources、tools；其可见集合可随授权、时间和服务器状态变化，配置元数据不能证明内容安全、质量或实际使用。[7]

**[推论]** 现有产品已有局部配置和检查入口，但没有由这些事实自动推出适合个人真实工作的稳定组合。机会是建立面向工作结果的跨资产装配体验，而不是再造资产目录或宣称统一所有客户端语义。

## 服务对象与核心工作

**[假设] 首要用户**是需要跨多类真实工作重复使用个人 Agent 资产、同时维护部分公共可复用资产的高自主性个人实践者。他们能表达目标和价值偏好，但不应被要求先掌握全部配置细节、方法空间或平台差异。

他们需要：

1. 为稳定工作场景获得“刚好合适”的 Instructions、Skills、MCP 组合及明确边界；
2. 在普通任务中快速激活已验证配置，而不是重新装配；
3. 看清期望装配、最终结果、差异、冲突、裁剪和未知；
4. 让公共复用资产与个人私域资产独立且可协同，不泄露私有内容；
5. 用真实任务验收配置价值，让 bad case 有边界地反哺体系。

候选次要用户是维护和消费公共可复用配置的其他个人。团队治理、组织级策略与商业化尚无证据，不纳入当前承诺。

## 产品体验

### 低频控制面：Context Assembly

新场景、明确优化需要或真实失败触发装配。Agent 主动调查事实、抽象需求、扩展方法空间，生成少量可区分候选并给出推荐、依据与未知；人只在权限、高风险、不可逆或价值取舍上确认，也可低成本拒绝、补充或保留未知。

装配产物说明适用工作、能力组合、结构化上下文入口、边界和变体；区分希望装配与最终生效；暴露差异、冲突、裁剪、来源和无法证明之处；分别记录装配忠实度、配置适用性、任务结果的证据；把跨 Session 需要的关键事实和决定交接为可检查产物。

### 高频工作面：Activation → Loading → Execution

普通任务激活已验证配置，经声明入口加载必要现场背景，然后执行并验收。安装、可用和本次激活均须可见；当目标、约束、权限或风险发生实质变化时，重新判断配置，而不是因为仍在同一 Session 就沿用旧能力面。

```text
稳定配置 → 快速激活 → 真实任务执行与验收 → bad case / 新需求 → 有边界的低频改进
```

Assembly 不拥有、复制或重新建模某次任务的动态内容。需求文档、当日日志、当前代码差异等仍是任务期输入；只有稳定、通用且经真实工作证明有价值的方法或入口，才进入低频配置。

## 当前范围与边界

**纳入**

- 稳定工作配置及其变体、适用边界和结构化上下文入口；
- Instructions、Skills、MCP 三类源资产的组合；
- 公共复用部分与个人私域部分的独立边界和授权协同；
- 期望装配、最终结果、差异、冲突、裁剪、来源和未知的检查；
- 装配忠实度、配置适用性、任务结果三层验证；
- 跨 Session 的关键事实、决定和证据交接，以及由真实 bad case 驱动的受控演进。

**明确不纳入**

- 广义 Context Loading、细粒度业务知识、项目背景或项目任务资产管理；
- Memory/RAG、模型参数、权限沙箱、Hooks、子 Agent 定义等同层级核心资产；
- 资产 taxonomy、目录布局、字段、存储方式、Canonical IR、Schema；
- CLI、适配器、TUI 或其他具体实现架构；
- OMP、Claude CLI、Codex CLI 之间的跨 CLI 对话恢复或配置等价；
- 强制 Hard Handoff、每任务实时 Skill discovery、现场任意生成动态子 Agent 装配；
- 把 Work Type × Subject × Situation、BMad、OpenSpec、SpecKit 或某组 micro methods 当作系统本体。

## 当前核心资产

| 核心资产 | 当前产品含义 | 必须守住的边界 |
| --- | --- | --- |
| Instructions | 系统、开发者与项目入口的稳定指令资产 | 不把任务动态背景塞入常驻指令；冲突和实际加载保持可见 |
| Skills | 可复用、可维护的方法与工作流包 | 历史存在不等于应保留；按来源、行为价值、适用边界和实际表现判断 |
| MCP | 服务器声明，以及 tools、resources、prompts 和服务端指令等带来的影响 | 配置不等于连接、批准、可调用或可信；动态能力与信任风险保持可见 |

Profile 或 Assembly 配置只用于组合这些源资产，不是第四类源资产，也不要求与工作模式一一对应。

## 产品原则

1. **执行优先**：任务实际完成和验收是北极星，配置管理只是手段。
2. **诚实证据**：声明、最终装配与运行观察分层；不知道就标为未知。
3. **低频维护，高频复用**：不在每次任务中实时重做完整方法发现和装配。
4. **公共复用、私域独立**：公共仓不保存个人私有资产或当前上下文，私域资产也不因此被排除。
5. **Agent 主动、人保留控制**：Agent 调查、抽象和推荐；人不必长篇总结，也始终可以拒绝或纠偏。
6. **真实失败驱动演进**：不因历史存在、方法流行或技术可做就扩张范围。

这不是已证明的技术护城河。差异来自约束纪律、证据诚实度，以及能否持续把装配转化为更好的任务结果。

## 成功标准

**北极星**：在代表性真实任务中，使用已验证配置后，任务一次验收通过率提高，同时任务期装配干预率和无关上下文减少。

首轮验证要求：

- 用户无需重新研究完整方法空间，即可说明为何选择此配置、适用工作和边界；
- 相同的已声明输入可重复得到可检查结果，无法证明的运行维度保持 `unknown`；
- 希望装配与最终结果的已知差异全部暴露，不静默丢弃或冒充成功；
- 每个候选稳定配置通过装配忠实度、工作适用性和真实任务验收三层检查；
- 普通任务不触发重装配，只有新场景、已知不足或 bad case 才进入低频改进；
- 公共产物不包含私有原文、凭据或个人当前上下文，私域引用不成为公共理解的必需依赖。

当前没有可信基线，不虚构百分比目标。下一阶段先建立一次验收率、装配干预率、无关上下文和失败类型基线，再决定量化门槛。

## 风险、未知与当前推荐

| 主题 | 风险 / 未知 | 当前推荐 |
| --- | --- | --- |
| 首批稳定配置 | 哪些场景能形成稳定配置尚未知 | 从少量高频且验收清晰的真实任务反推，不先设计完整 catalog |
| Profile 语义 | 可能只是激活入口，也可能承担更多语义 | 先按最轻的激活与复用概念处理；只有 bad case 证明不足时扩张 |
| Soft / Hard 切换 | Hard Handoff 的收益与成本无真实证据 | 默认 Soft Switch；仅在干扰、权限或隔离证据出现时重评 |
| Skill discovery | 触发、成本和停止条件未定 | 继续停放，不阻塞“稳定配置—激活—执行—验收”闭环 |
| 外部方法包 | BMad、SpecKit、Matt Skills 等价值未知 | 按来源、行为价值、适用边界和真实表现逐项评估 |
| 验证分界 | 机械检查与低成本语义判断边界未定 | 优先机械验证；仅把机器无法判断的问题交给低成本模型 |
| 第四类资产 | 未来可能有真实案例要求扩展 | 不预留抽象；必须由具体需求或 bad case 重新评估 |
| 平台漂移 | 客户端加载、覆盖、批准和调用语义会变化 | 持续核验外部语义，不承诺未经观察的等价性 |
