# Agent Context Assembly 产品需求文档

## 0. 文档目的与权威边界

本文定义 Agent Context Assembly 的产品需求，供后续 UX、架构与史诗拆分使用。本文与同工作区 `addendum.md` 已蒸馏全部仍有效的批准输入，二者共同构成下游自足合同；`addendum.md` 只保留架构阶段候选与技术边界，不得新增或覆盖本文的产品范围。原始 `brief.md` 与其补充只保留来源作用；本文不从旧 brainstorming、历史材料或既有实现恢复额外需求。

本文只定义用户结果、产品能力、边界与验收，不规定 CLI、TUI、适配器、存储、Schema、Canonical IR 或实现语言。现有 Python CAP 只提供问题、反例和概念可行性证据，不是需求合同、迁移基线或目标实现。TypeScript 仅是后续架构阶段需要比较的候选方向。

## 1. 产品愿景与核心判断

Agent Context Assembly 面向长期借助 Agent 完成多类真实工作的个人实践者。它把分散、重复、质量不一的 Instructions、Skills 与 MCP 装配成可复用、可重复激活且可检查的稳定配置，使用户不必在每次任务开始时重新研究方法空间、能力来源和平台生效细节，而能把主要精力用于完成并验收真实工作。

产品由两个节奏不同但相互闭环的工作面组成：

1. **低频 Context Assembly**：只在新场景、已知不足或真实 Bad Case 出现时，调查事实、抽象需求、生成候选、形成稳定配置并完成验证；
2. **高频 Activation → 声明入口式 Context Loading → Task Execution**：普通任务复用已验证的稳定配置，通过声明入口取得任务期输入，执行任务并按任务自身标准验收。

核心产品判断是：可靠性不来自“管理更多配置”，而来自更少的任务期装配干预、对来源和生效状态的诚实呈现，以及用真实任务结果持续淘汰不合适的能力组合。产品不承诺统一不同客户端的语义，也不把配置存在冒充为实际生效。

## 2. 服务对象与待完成工作

### 2.1 首要用户

**[ASSUMPTION]** 首要用户是高自主性的个人实践者：长期跨多类工作使用 Agent，能表达目标、约束和价值偏好，同时维护公共可复用资产与个人私域资产；但不应被要求先掌握全部配置细节、方法空间或平台差异。本假设继承自已批准 Brief，并在首批真实任务验证后复核。

维护或消费公共复用配置的其他个人不是 MVP 行为主体；MVP 不提供面向该角色的发现、共享或消费流程。公共产物可独立理解是隐私与可移植边界，不等于承诺次要用户体验。团队治理、组织级策略与商业化也不属于当前承诺。

### 2.2 Jobs To Be Done

- 当出现稳定工作场景时，获得一组“刚好合适”的 Instructions、Skills、MCP 及其适用边界，而不是自己从全部资产中枚举和拼装。
- 在普通任务中快速激活已经验证的稳定配置，不重复做完整发现、比较和装配。
- 在出错前后都能看清期望装配、最终结果、差异、冲突、裁剪、来源和 Unknown，不把静默缺失误判为成功。
- 让公共复用资产和个人私域资产在授权环境中协同，同时避免私有原文、凭据和个人当前上下文进入公共产物。
- 用真实任务验收稳定配置的价值，并把 Bad Case 转化为有边界、可追溯的低频改进。

### 2.3 核心工作流

- **WF-1：建立或修订稳定配置。** 新场景、已知不足或 Bad Case 触发 Context Assembly。Agent 调查事实并提出少量候选与推荐；用户只处理涉及权限、高风险、不可逆操作或价值取舍的决定。产出是有适用边界和证据的稳定配置，不是一次任务的动态内容副本。
- **WF-2：复用稳定配置完成普通任务。** 用户激活稳定配置，经声明入口加载必要的任务期输入，查看本次可观察状态，执行并验收真实任务。没有新场景、已知不足或 Bad Case 时，不回到完整装配。
- **WF-3：由失败驱动有界演进。** 真实任务失败后，产品区分装配忠实度、配置适用性和任务结果问题，只修改证据指向的部分；关键事实、决定与证据可跨 Session 检查和续接。

## 3. 术语

- **源资产**：可参与装配的 Instructions、Skills 或 MCP。稳定配置不是第四类源资产。
- **Instructions**：系统、开发者与项目入口中的稳定指令资产；不包含某次任务的动态背景。
- **Skills**：可复用、可维护的方法与工作流包；历史存在不等于当前应保留或本次已加载。
- **MCP**：服务器声明及其 tools、resources、prompts 和服务端指令带来的能力与影响；配置不等于连接、批准、可调用、可信或已实际使用。
- **Context Assembly**：为稳定工作场景调查、选择、组合并验证源资产的低频过程。
- **稳定配置**：经验证、可重复激活的源资产组合，包含适用工作、边界、变体和结构化上下文入口。它不拥有任务期输入。
- **Profile Activation**：为一次任务选择并激活稳定配置的高频动作。Profile 是激活与复用概念，不是源资产。
- **声明入口式 Context Loading**：通过稳定配置声明的入口取得某次任务所需动态背景；动态背景仍由其原始载体拥有。
- **任务期输入**：需求文档、当日日志、当前代码差异、远端当前合同等只对具体任务成立的内容。
- **期望装配**：根据稳定配置和本次声明输入，应参与任务的源资产及状态。
- **最终结果**：产品在本次环境中实际得到或观察到的装配结果；不可观察部分必须保留为 Unknown。
- **Unknown**：现有证据不能证明的状态或结论，不得被默认值替换为成功或失败。
- **装配忠实度**：期望装配与最终结果是否一致，及所有已知差异是否被暴露。
- **配置适用性**：稳定配置对目标工作是否必要、充分且不过载。
- **任务结果**：真实任务是否按其独立验收标准完成。
- **Bad Case**：真实任务中暴露的失败、干扰、能力缺失或错误生效证据；不是未经验证的改进灵感。
- **公共复用资产**：可在公共产物中自足理解和复用的源资产；不得以私域内容作为理解前提。
- **个人私域资产**：只在其原有授权环境中可用的源资产；可以参与装配，但原文、凭据和个人当前上下文不得进入公共产物。
- **运行观察**：客户端或任务执行表面在特定时间提供的可回读证据；其结论不得超出观察边界。
- **Soft Switch**：在原运行连续性内重新判断或更换稳定配置，不强制建立隔离的交接边界。
- **Hard Handoff**：通过新的隔离运行边界交接任务；MVP 不默认要求。
- **Skill Discovery**：识别可能适用的 Skills 并判断是否加载的过程；MVP 不在每个普通任务中实时重做。
- **工作目录（Catalog）**：预先枚举工作类型与稳定配置的完整集合；MVP 不先建设完整 Catalog。

## 4. 代表性真实任务候选与首批推荐

### 4.1 选择标准

首批样本必须同时满足：实际发生频率较高、完成标准清楚、能力组合有明显差异、可在可控权限下重复观察。首批验证不追求覆盖完整工作目录；目标是尽快判断“稳定配置—激活—执行—验收”闭环是否产生价值。

### 4.2 候选

| 候选 | 真实任务及可观察完成标准 | 预期能力差异 | 首批判断 |
| --- | --- | --- | --- |
| T-1 产品需求产出 | 从已批准 Brief 与补充边界创建中文 PRD；完成标准是来源覆盖、FR 可验收、范围无扩张、无架构偷跑 | 强项目 Instructions、PRD/审阅 Skills；MCP 不是必需项，可验证“刚好合适”允许主动不装配 | **推荐首批**；本次 PRD 即可作为首个真实样本 |
| T-2 官方来源技术核验 | 核验多个当前官方来源并形成带链接的事实摘要；完成标准是事实/推论分离、来源可回读、不宣称跨平台等价 | 证据与引用 Instructions、研究 Skills、外部来源访问类 MCP；动态连接与信任状态更突出 | **推荐首批**；可与 T-1 同期取得样本 |

### 4.3 已确认首批任务

**负责人已确认首批验证采用 T-1、T-2、T-3。** 它们分别覆盖结构化产品产出、只读证据研究和有状态代码执行，验收标准清晰且能力组合差异最大。若近期没有公开、自足且明确授权的 T-3 Issue，则按已确认选项用 T-4 替代，并记录替代理由。T-5 暂不进入首批，避免把授权失败或远端流程变化误归因为稳定配置失败。

该集合只定义首轮验证样本，不固化为永久 Catalog。首批结果只允许支持或推翻当前配置假设，不自动扩展产品范围。

### 4.4 已确认 MVP 客户端范围

**MVP 只承诺一个真实 Agent 客户端运行环境，本文统一称为“OMP Agent 单客户端环境”。** MVP 必须在该环境中完成稳定配置、激活、执行与验收闭环，并诚实呈现其可观察状态。每个基线与稳定配置样本都必须记录可回读的客户端身份、版本或等价环境证据；具体版本值留在样本记录，不在 PRD 固化。Claude Code 与 Codex 官方语义只作为平台差异和证据边界的事实输入，不构成第二、第三客户端支持承诺。出现第二客户端的重复真实任务或 Bad Case 时，才重新评估扩大覆盖；MVP 不承诺跨客户端配置等价。

## 5. 产品能力与功能需求

### 5.1 面向真实工作的低频 Context Assembly

#### FR-1：有边界的装配触发

个人实践者可以因新场景、已知不足或 Bad Case 启动 Context Assembly；普通任务复用不得自动触发完整装配。实现 WF-1、WF-2。

**可验收结果：**
- 每次 Context Assembly 都能指出触发原因及其对应的真实工作或证据。
- 重复执行普通任务时，只有在目标、约束、权限和风险均未发生实质变化的情况下，产品才继续复用稳定配置。
- “发现更多资产”“历史上存在某资产”或“技术上可以装配”本身不能成为扩张稳定配置的理由。

#### FR-2：Agent 主动调查、抽象与推荐

Agent 能从用户提供的目标、约束、验收、当前环境和授权来源中主动调查事实、抽象稳定需求、扩展合理方法空间，并提出少量可区分候选与一个明确推荐。实现 WF-1。

**可验收结果：**
- 用户无需从零枚举全部 Instructions、Skills、MCP 或方法空间。
- 每个候选都说明适用工作、拟用源资产、边界、主要差异、推荐依据、风险和 Unknown。
- BMad、SpecKit 或其他外部方法包必须按来源、行为价值、适用边界和真实表现逐项评估；知名度、安装状态或历史使用不能替代评估。
- 候选集合默认包含 2～3 个，最多 4 个：只有现有候选无法表达一个具名价值取舍时才增加第 4 个；若只有一个可信候选，必须说明其他替代为何违反已知边界。达到该条件即停止扩展，不用长目录替代产品判断。
- 用户可以拒绝、补充或纠偏；只有涉及权限、高风险、不可逆操作或价值取舍的决定必须升级给用户确认。

#### FR-3：形成稳定配置而不吞并任务期输入

个人实践者可以保存并复用经验证的稳定配置，包括适用工作、必要源资产、变体、边界和结构化上下文入口。实现 WF-1、WF-2。

**可验收结果：**
- 稳定配置只纳入对该工作稳定且经真实任务证明有价值的源资产；不要求三类源资产必须全部出现。
- Profile 只承担稳定配置的激活与复用语义，不被当作第四类源资产，也不要求与稳定工作场景一一对应。
- 需求文档、当日日志、当前代码差异、远端当前合同等任务期输入仍由原始载体拥有；稳定配置只声明如何取得它们。
- 同一稳定工作需要有限变体时，变体继承共同边界并明确差异，不复制成无关系的配置。

### 5.2 来源、边界与装配可检查性

#### FR-4：源资产来源与公共/私域边界

个人实践者可以在授权环境中组合公共复用资产与个人私域资产，同时保持二者独立边界。实现 WF-1、WF-2。

**可验收结果：**
- 每个参与装配的源资产都能追溯到来源类别与当前可观察状态。
- 公共产物不包含私有原文、凭据或个人当前上下文；公共读者无需访问私域内容即可理解稳定配置的产品含义和边界。
- 私域资产未授权、不可达或无法核验时，最终结果明确显示差异或 Unknown，不以公共替代物静默顶替。
- 产品不因资产位于私域而将其排除，也不因已获授权而复制其内容到公共范围。

#### FR-5：区分期望装配、最终结果与运行观察

个人实践者可以分别查看期望装配、最终结果和可获得的运行观察。实现 WF-1、WF-2、WF-3。

**可验收结果：**
- 产品按客户端实际可观察语义区分配置或安装、发现或启用、连接或批准、本次激活、实际调用或生效等维度；平台没有提供的维度保持 Unknown。
- MVP 的通过门只适用于 §4.4 已确认的单一运行环境；其他客户端的文档或观察只能证明平台差异，不能冒充该客户端已获产品支持。
- 不同客户端的状态不被强行映射成未经证明的等价状态。
- 文件存在、配置通过静态检查、服务器连接或能力列出，均不能单独证明本次任务实际使用或产生效果。
- 运行观察必须说明证据来源及其观察边界。

#### FR-6：暴露差异、冲突、裁剪与 Unknown

个人实践者可以检查期望装配与最终结果之间的所有已知差异，以及源资产之间可识别的冲突、裁剪和覆盖；无法判断的部分保留为 Unknown。实现 WF-1、WF-2。

**可验收结果：**
- 已知缺失、额外出现、被禁用、被覆盖、因预算或限制被裁剪的源资产均不静默消失。
- “已知差异”必须由期望装配、最终结果、客户端状态或任务证据中的至少一项直接显示不一致；缺少证据时记录 Unknown，不把推测计作差异。机械证据不能裁决语义影响时，由 Agent 给出判断依据；用户只裁决涉及价值取舍、高风险或不可逆影响的问题。
- 每项差异说明影响范围；无法判断影响时明确为 Unknown。
- 冲突只在有证据时标记，不把不同来源并列或顺序差异自动宣称为语义冲突。
- 产品不以“检查通过”替代最终结果或任务结果验证。

#### FR-7：可重复得到可检查结果

在相同声明输入和相同可观察外部条件下，个人实践者可以重复得到可检查的最终结果；外部状态变化必须作为差异出现。实现 WF-1、WF-2。

**可验收结果：**
- 重复装配能追溯使用了哪些声明输入、源资产来源和外部状态证据。
- 动态 MCP 能力、授权、客户端版本或来源发生变化时，结果不伪装成与上次相同。
- 不可观察维度在重复运行中继续保持 Unknown，除非出现新的有效证据。
- “可重复”指结果与差异可解释、可检查，不要求忽略动态外部状态的字节级相同。

### 5.3 高频 Activation、声明入口式 Context Loading 与 Task Execution

#### FR-8：快速激活已验证稳定配置

个人实践者可以为普通任务选择并激活已验证的稳定配置，并在执行前看见与本次相关的可观察状态。实现 WF-2。

**可验收结果：**
- 激活过程不要求重新完成方法发现或全量资产比较。
- 普通复用路径不得要求用户选择或修改单项源资产，不得重复输入产品已能从声明入口取得的目标、约束或验收；除客户端自身要求的认证或权限动作外，最多只需要一次稳定配置激活确认。
- 产品明确区分稳定配置已声明、源资产当前可用和本次已激活；缺少证据时保持 Unknown。
- 激活不能因仍在同一 Session 就继承已经失效的目标、约束、权限或风险假设。
- 激活失败时保留失败原因和受影响能力，不冒充已完成。

#### FR-9：通过声明入口加载任务期输入

稳定配置可以声明完成目标工作需要的上下文入口；个人实践者在任务期从这些入口取得该任务所需的当前内容。实现 WF-2。

**可验收结果：**
- 稳定配置说明需要哪类任务期输入及其取得入口，但不复制或重新建模输入内容。
- 缺失、过期、无权访问或无法确认新鲜度的任务期输入在执行前可见。
- 任务期输入的变更不会自动修改稳定配置；只有它暴露新场景、已知不足或 Bad Case 时才触发 Context Assembly。
- 广义业务知识管理、Memory/RAG 和项目任务资产管理不因此进入产品范围。

#### FR-10：在实质变化时重新判断

当任务目标、约束、权限或风险发生实质变化时，产品要求重新判断稳定配置是否仍适用。实现 WF-2、WF-3。

**可验收结果：**
- 重新判断的原因与受影响边界可检查。
- “实质变化”指任务验收、适用权限、私域暴露、不可逆风险或必需能力中的任一项改变；仅措辞变化或不改变这些条件的任务期输入更新不是实质变化。无法判断时保持 Unknown，并在执行依赖该判断前升级。
- 不构成实质变化的更新不触发完整 Context Assembly。
- 同一 Session、同一仓库或同一 Profile 名称都不能单独证明稳定配置仍适用。
- 重新判断可以得出“继续使用原稳定配置”，不强制制造变更。

### 5.4 三层验证与受控演进

#### FR-11：分别验证三层结果

每个候选稳定配置必须分别接受装配忠实度、配置适用性和任务结果验证。实现 WF-1、WF-2、WF-3。

**可验收结果：**
- 装配忠实度检查期望装配与最终结果及全部已知差异。
- “必要”要求有证据表明移除该能力会失去任务验收条件或必需证据；“充分”要求不存在已知未满足的任务验收条件；“不过载”要求每项引入能力或上下文都能追溯到目标、约束、验收或证据需要。无法判断的项目记录为 Unknown，不得宣布配置适用性通过。
- 配置适用性检查能力是否必要、充分、不过载，并记录无关上下文和任务期装配干预。
- 任务结果使用该真实任务自身的验收标准，不用装配检查代替。
- 三层证据分别记录；任一层成功都不能自动推出其他层成功。

#### FR-12：建立首轮基线而不虚构目标

产品可以围绕选定真实任务记录当前基线及使用稳定配置后的结果，为后续量化门槛提供证据。实现 WF-1、WF-2。

**可验收结果：**
- 每个首批任务至少记录：一个当前基线样本和两个稳定配置样本，其中至少一个稳定配置样本来自新 Session；不可重复的一次性任务使用同一任务类型、同一验收结构的独立实例。
- “可比较”要求任务类型与验收口径一致，并记录声明输入、OMP Agent 客户端身份、客户端版本（或等价环境证据）以及已知外部变化；不满足时分组呈现，不能合并计算。
- 每个样本记录一次验收结果、任务期装配干预、无关上下文、已知差异与失败类型。“无关上下文”指无法追溯到目标、约束、验收或证据需要的内容或能力；无法判断时记录 Unknown。
- 在没有可信基线前不填入虚构百分比目标。完成最小样本后，负责人必须决定接受稳定配置、调整稳定配置、停止本轮验证，或追加一次能区分具名未知的采样；追加一次仍不能区分时再次升级，不得无限采样。

#### FR-13：由 Bad Case 驱动有界改进

个人实践者可以把真实 Bad Case 归因到对应验证层，并只修改证据指向的稳定部分。实现 WF-3。

**可验收结果：**
- 每个改进都链接到具体 Bad Case、新场景或已知不足，并说明改变了什么、为什么。
- 临时任务背景不因一次失败进入稳定配置。
- 对 Profile 语义、Hard Handoff、每任务 Skill Discovery、动态子 Agent 装配或第四类核心资产的扩张，必须由具体证据重新评估，不能作为默认修复。
- 没有证据支持修改时，“不改变稳定配置”是合法结果。

#### FR-14：跨 Session 交接关键事实、决定与证据

个人实践者可以在不同 Session 之间检查并续接与稳定配置有关的关键事实、决定和证据。实现 WF-1、WF-3。

**可验收结果：**
- 交接产物区分事实、推论、决定、证据和 Unknown。
- 新 Session 不需要依赖不可检查的旧对话即可理解当前稳定配置的适用边界和未决项。
- 交接不恢复旧授权、当前任务状态或动态上下文，也不承担跨 CLI 对话恢复。
- 被新证据替代的决定保留可追溯关系，不静默改写历史含义。

## 6. 跨领域质量要求与产品护栏

### 6.1 证据诚实度

- **NFR-1**：所有成功、失败、差异和生效结论都必须绑定其证据层级；未知即 Unknown。
- **NFR-2**：静态声明、最终装配和运行观察必须可区分；不得通过命名或汇总把较弱证据提升为较强结论。
- **NFR-3**：平台语义随客户端版本、授权、时间或服务器状态变化时，观察结果必须带有足以理解其有效边界的信息。

### 6.2 隐私与授权

- **NFR-4**：公共产物不得包含私有原文、凭据或个人当前上下文。
- **NFR-5**：任何私域资产参与装配都受其原有授权边界约束；产品不得通过复制、缓存或公共摘要绕过授权。
- **NFR-6**：外部来源或 MCP 提供的元数据、内容和能力不得因“已配置”自动视为安全、可信或适合任务。

### 6.3 维护成本与可控性

- **NFR-7**：普通任务的默认路径是激活和执行，不是重新装配；产品不得以提高配置管理活动量作为成功代理。
- **NFR-8**：优先使用可重复的机械检查；只对机器无法判断的适用性、冲突含义或任务结果进行有边界的语义判断；无法判断的部分保留为 Unknown。
- **NFR-9**：Agent 负责调查、抽象和推荐；用户保留拒绝和补充的权利，以及高风险事项的决定权，不被迫提交完整资产目录或长篇方法总结。

## 7. 明确非目标

当前产品不做：

- 面向业务知识、项目背景或任务资产管理的上下文平台；MVP 只包含声明入口式 Context Loading；
- 把 Memory/RAG、模型参数、权限沙箱、Hooks 或子 Agent 定义视为与 Instructions、Skills、MCP 同层级的核心资产；
- 资产 taxonomy、目录布局、字段、存储方式、Canonical IR 或 Schema；
- CLI、适配器、TUI、存储或其他具体实现架构；
- OMP、Claude CLI、Codex CLI 之间的跨 CLI 对话恢复或配置等价；
- 第二个或更多 Agent 客户端的产品支持；扩大覆盖必须由重复真实任务或 Bad Case 触发（**2026-08-23 更新**：该触发条件已就 Claude Code/Codex 达成，两者升格为已激活的第二类客户端 adapter，纳入 Epic 4；范围限定为各自的类型化能力装配，不构成配置或 Session 等价、不构成三端同步、不构成对 Claude Code/Codex 之外任何客户端的支持承诺，详见本节上方 §4.4 的裁决更新与 `sprint-change-proposal-2026-08-23-cap-claude-codex-adapter.md`）；
- 强制 Hard Handoff、每任务实时 Skill Discovery、现场任意生成动态子 Agent 装配；
- 把 Work Type × Subject × Situation、BMad、OpenSpec、SpecKit 或任一组 micro methods 当作系统本体；
- 面向其他个人的公共配置发现、共享或消费流程；
- 团队治理、组织级策略、商业化或完整工作目录（Catalog）；
- 把现有 Python CAP 行为视为必须保留的需求，或在本阶段决定 TypeScript 实现。

## 8. MVP 范围

### 8.1 纳入

- 面向稳定工作场景的 Context Assembly 触发、主动调查、少量候选与推荐；
- Instructions、Skills、MCP 的必要组合、有限变体、适用边界和结构化上下文入口；
- 公共复用资产与个人私域资产在授权环境中的独立协同；
- 期望装配、最终结果、来源、差异、冲突、裁剪和 Unknown 的检查；
- Profile Activation、声明入口式 Context Loading 与普通任务复用；
- 装配忠实度、配置适用性、任务结果三层验证；
- 围绕已确认的 T-1、T-2、T-3 建立真实任务基线；无合适 T-3 Issue 时按已确认选项以 T-4 替代；
- 在 §4.4 确认的单一 OMP Agent 运行环境内完成闭环；Claude Code/Codex 第二客户端已按 §4.4 的 2026-08-23 裁决更新激活，其装配能力属于 Epic 4，不在本节所述的既有 MVP（Epic 1～3）交付范围内；
- 跨 Session 关键事实、决定和证据交接；
- Bad Case 驱动的受控演进。

## 9. 成功标准与验证计划

### 9.1 北极星与度量定义

- **SM-1 一次验收通过率**：代表性真实任务在首次正式验收时通过的比例。验证 FR-8、FR-9、FR-11。当前先建立基线，不设虚构百分比。
- **SM-2 任务期装配干预率**：普通任务中需要重新研究、替换或补充稳定源资产的任务占比。验证 FR-1、FR-2、FR-8；方向为下降。
- **SM-3 无关上下文**：按 FR-12 判定，主口径分别记录每个样本的无关内容条目数与无关能力条目数，不把两类条目合并；另报告出现至少一项无关上下文的样本占比。验证 FR-3、FR-11、FR-12；当前只建立基线，后续方向为两类条目数和出现率均减少。
- **SM-4 装配可解释率**：首批候选中，能够说明选择理由、适用工作、边界、来源和全部已知差异的比例。验证 FR-2、FR-4、FR-6；MVP 要求每个被接受候选均满足。
- **SM-5 三层证据完备率**：首批候选中，同时具备装配忠实度、配置适用性和任务结果证据的比例。验证 FR-11、FR-12；MVP 要求每个被宣布为“已验证”的稳定配置均满足。
- **SM-6 激活负担**：普通复用路径中的单项源资产选择次数、重复输入次数和产品要求的激活确认次数。验证 FR-8；MVP 门为前两项均为零，除客户端自身认证或权限动作外激活确认不超过一次。

### 9.2 反指标

- **SM-C1 装配维护活动量**：配置数、修改次数或 Skill Discovery 次数增加不代表成功；它们上升可能说明产品制造维护负担。制衡 SM-2、SM-4。
- **SM-C2 能力数量**：更多 Instructions、Skills 或 MCP 不代表更合适；能力数量不得作为质量代理。制衡 SM-3。
- **SM-C3 Unknown 压低率**：通过把 Unknown 改写成成功来提高表面通过率属于失败。制衡 SM-1、SM-4。

### 9.3 首轮验收门

1. 已确认首轮任务为 T-1、T-2、T-3；无合适 T-3 Issue 时以 T-4 替代并记录理由。
2. 每项首批任务获得 FR-12 规定的最小可比较证据：一个当前基线样本、两个稳定配置样本，且至少一个稳定配置样本来自新 Session。
3. 每个稳定配置都能说明其选择理由、适用工作和边界，并明确列出不装配的能力；用户无需重新研究完整方法空间。
4. 普通复用路径满足 SM-6 的激活负担门，不要求用户处理单项源资产选择或重复输入。
5. 相同声明输入与相同可观察条件可重复得到可检查结果；所有无法证明的运行维度保持 Unknown。
6. 期望装配与最终结果之间的全部已知差异按 FR-6 判定并暴露，不静默丢弃或冒充成功。
7. 每个被宣布为“已验证”的稳定配置通过三层检查；任务结果必须按各任务独立标准验收。
8. 普通重复任务不触发完整 Context Assembly；只有新场景、已知不足或 Bad Case 进入低频改进。
9. 公共产物不包含私有原文、凭据或个人当前上下文，且不依赖私域内容才能理解。
10. 最小样本完成后，负责人按 FR-12 决定接受稳定配置、调整稳定配置、停止本轮验证，或追加一次有区分力的采样；随后再确定 SM-1、SM-2、SM-3 的量化目标，不虚构门槛。

## 10. 风险与缓解

| 风险 | 产品层缓解 |
| --- | --- |
| 尚不知道哪些场景能形成稳定配置 | 只从 T-1、T-2、T-3/T-4 的真实结果反推，不先建完整 Catalog |
| Profile 语义被过度扩张 | MVP 只按最轻的激活与复用概念处理；具体 Bad Case 才能触发重评 |
| 平台加载、覆盖、批准和调用语义漂移 | 保留客户端特有状态、证据边界和 Unknown；不承诺跨客户端等价 |
| MCP 动态能力或外部内容不可信 | 区分配置、连接、批准、可调用和实际使用；元数据不自动获得信任 |
| 外部方法包因知名度或已安装状态被误判为适用 | 按来源、行为价值、适用边界和真实任务表现逐项评估，不把 BMad、SpecKit 或其他方法包当作系统本体 |
| 公共/私域协同导致泄露 | 公共产物只保留理解产品边界所需信息，不复制私有原文、凭据或当前上下文 |
| 验证结果被实现现状绑架 | Python CAP 仅作问题与反例来源；需求与验收以已批准的产品合同为依据重新判断 |
| 机械检查与语义判断边界失控 | 机械检查优先；只对无法机械判断且影响验收的问题进行有边界的语义判断 |
| 首轮样本把权限或流程故障误判为稳定配置失败 | 首批暂缓 T-5；每个失败按装配忠实度、适用性、任务结果分层归因 |

## 11. 已知未知与重评条件

以下项目当前不阻塞 PRD，也不在本阶段作额外产品承诺：

- **量化门槛**：按 FR-12 的最小样本与退出规则取得基线后，由负责人根据 SM-1、SM-2、SM-3 的可比较数据确认；只允许一次针对具名未知且能区分结果的追加采样。
- **Profile 是否需要更多语义**：只有最轻激活与复用不能解释具体 Bad Case 时重评。
- **Soft Switch / Hard Handoff**：默认保持 Soft Switch；只有干扰、权限或隔离证据出现时重评 Hard Handoff。
- **每任务 Skill Discovery**：继续停放；只有稳定配置无法覆盖的重复 Bad Case 出现时重评触发、成本和停止条件。
- **第四类核心资产**：不预留抽象；只有 Instructions、Skills、MCP 无法表达的具体需求出现时重评。
- **实现语言与产品表面**：留给架构阶段；TypeScript 必须与其他允许语言按运行环境、集成面、类型与测试、分发和维护成本比较。产品表面不得反向扩大 §4.4 的单一客户端范围。

## 12. 假设索引

- §2.1：首要用户是跨多类真实工作、同时维护公共与私域 Agent 资产的高自主性个人实践者；在首批真实任务后复核。
