# Addendum 输入核对

## 结论

PRD 与输出 addendum 保持了输入 addendum 的两项核心边界：TypeScript 只在后续架构阶段作为候选比较，现有 Python CAP 只作问题、概念与反例证据。核对发现的两处表述偏差已修正。

## 已覆盖

- TypeScript 不是当前产品决定或既定架构；
- 后续比较维度包括运行环境、客户端集成面、类型与测试支持、分发方式和长期维护成本；
- Python CAP 不是目标架构、迁移基线或必须保留的行为合同；
- 后续建设从已确认的产品目标、范围与验收重新判断；
- 当前不进入 CLI、Schema、IR、适配器或具体实现架构。

## 发现与处置

1. **遗漏“当前不做 Python CAP 代码审计”。** 原稿只排除了重写和迁移设计。已在输出 addendum §3 明确加入 Python CAP 代码审计。
2. **技术比较范围被无依据缩窄。** 原稿写成“本仓允许的其他语言”，而输入只要求“其他允许语言”。已恢复输入表述，避免提前把架构比较限制在仓库贡献规则。

## 联合输入边界说明

PRD 中 Soft Switch、Hard Handoff、每任务 Skill discovery、动态子 Agent 装配及跨 CLI 等价的边界来自已批准 Brief，不是从输入 addendum 擅自扩展；这些内容仅作为默认边界、非目标或重评条件出现，没有定义实现机制。

## 违规检查

- **架构偷跑：** 未发现。TypeScript 没有被选定，技术概念只在排除项和架构阶段交接中出现。
- **旧实现需求化：** 未发现。Python CAP 的既有行为、接口和架构均未写成需求。
