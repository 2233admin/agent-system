# 三 CLI 装配架构决策研究简报

## 决策

在以下三种路径中选择总成本最低、可逆性足够的 Agent System 架构：

1. 一步支持 OMP、Claude Code、Codex CLI；
2. 外部核心与最窄 adapter contract，OMP-first；
3. OMP 内部特化，后续再抽取。

## 硬门

- 后续必须能支持 OMP、Claude Code、Codex CLI。
- 不要求语义等价；允许 unsupported、degraded、Unknown。
- 外部选择装配后，应能按客户端能力恢复同一 Session。
- 私域配置、Session 状态和凭据不进入公共仓。
- 现有 Python CAP 不是迁移基线。
- MVP 不以高 Token 多装配对照实验为发布门。

## 权重

- 首版与长期总成本：40%
- 首个可用 MVP 速度：25%
- 未来客户端接入成本：20%
- 可观察性与正确性：10%
- 分发与维护：5%

## 需要证伪的低成本假设

用户认为三端可能都能通过清空或隔离全局配置，再用配置文件和 CLI 参数装配 Skills、MCP、系统提示词；实现可能只需少量脚本。研究必须核实：各端是否支持可定位、可恢复、并发安全的配置覆盖；哪些能力只在启动时读取；如何选择/恢复 Session；直接清空全局配置的破坏性、竞态和回滚成本；是否真的需要常驻服务、SQLite、完整 adapter API 或 OMP 内部插件。

## 研究分解

- 客户端能力面：三端官方配置、参数、插件/hooks、Skills、MCP、系统提示词、Session resume、观察与分发。
- 架构与成本：脚本覆盖、外部核心+adapter、三端同时实现、OMP 内部特化的建设/维护/迁移成本。
- 实现与长期维护：语言、分发、测试矩阵、版本耦合、状态所有权、最低可逆性方案。
