# Agent Context Assembly：产品意图

## 要解决的问题

个人 Agent 资产长期散落、重复且质量不一。面对不同真实工作，Agent 需要的领域知识、方法、指令、Skills、MCP 和背景并不相同；错误选择、错误背景、能力缺口与未被暴露的漂移，会直接损害工作结果。目标是以当前公开 `agent-system` 仓库承载可公开复用部分，同时保留个人私有资产与上下文的边界，建立一套低频维护、可重复启用、可检查验证的工作配置体系，让人不必记忆各处隐式配置，也不必在每次任务开始时重新研究如何装配，而能把主要精力用于完成实际工作。

价值不在“管理配置”本身，而在于：为常见工作可靠提供刚好合适的能力和入口；让声明、最终装配结果、差异与未知可见；让关键事实和决定可交接；再用真实失败低成本改进体系，减少无关上下文、冲突和静默漂移。

## 当前核心范围

当前核心源资产只包括：

- **Instructions**：系统、开发者及项目入口指令资产；
- **Skills**：可复用、可维护的技能包；
- **MCP**：服务器声明及其带来的工具、资源、提示和服务端指令等影响。

Profile 或 Assembly 配置用于组合这些源资产，不是第四类源资产，也不要求与某种工作模式一一对应。一个稳定模式可以有变体、组合和适用边界。

## 运行边界

- **低频控制面——Context Assembly**：在出现新场景、优化需要或真实 bad case 时，建模和维护稳定工作配置，组织适用能力与结构化上下文入口，并检查其装配结果。它应帮助构建和改进自身，形成受控的 self-hosting 闭环。
- **高频工作面——Profile Activation / Context Loading / Task Execution**：普通任务优先激活已验证配置，经已知入口加载现场背景，再执行和验收工作；不在每次任务中重新求解完整方法空间或实时重做装配。
- Assembly 只提供稳定配置及上下文入口，不拥有、复制或重新建模每个任务的动态内容。某次需求文档、当日日志、当前代码差异等属于任务期输入；稳定的通用方法或流程才可能进入低频配置。

## 装配产物必须具备的能力

装配产物应是稳定、可复用、可重复激活、可检查的 Agent 工作配置，并且：

- 说明适用工作、能力组合、结构化上下文入口、边界和变体；
- 区分“希望装配什么”与“最终渲染或生效了什么”，让差异、冲突、裁剪和无法证明之处可见，不能把未知伪装成一致；
- 能展开、检查、比较和验证，便捷写法不能成为隐藏真相；
- 默认优先机械化验证与差异检查，仅在机器无法判断的语义问题上使用低成本模型；
- 同时关注装配是否忠实、配置是否适合工作、任务产物是否通过实际验收，不能用其中一层代替另外两层；
- 安装、可用与本次激活不可静默混同，资产存在不等于进入当前工作现场。

## 人机分工

Agent 主动承担事实调查、抽象总结、扩展用户尚未知的方法空间、生成少量可区分候选、给出推荐与依据，以及维护交接资产。人提供原始意图和价值偏好，在权限、高风险或不可逆取舍上确认，并通过观察输出和检查资产纠正漂移。任何候选都必须允许人拒绝、补充或明确表示未知；人的控制权不应被实现为要求人先掌握答案或撰写长篇声明。

## 资产交接与演进

任何需要跨 Session 继续使用的关键事实、决定和证据，都应进入可检查的结构化产物，不能只留在历史对话中。恢复历史 Session 是局部连续性的便利路径；新 Session 读取上一阶段产物是显式交接路径。若历史对话与当前有效产物冲突，应暴露冲突而非静默漂移；具体裁决机制尚未决定，当前只要求冲突可见。

体系从真实工作与 bad cases 受控演进：普通任务复用稳定配置；只有新场景、已知不足或失败证据才触发有边界的更新。有效实验应沉淀为可维护资产或配置修订，现有 Skills 也需要依据来源、行为价值、适用边界和实际表现重新判断，而非因历史存在而默认保留。

## 明确不做

当前不把以下内容纳入范围或既定方案：

- OMP、Claude CLI、Codex CLI 之间的跨 CLI 对话恢复或配置等价；
- 广义 Context Loading，以及细粒度业务知识、项目背景和项目任务资产的管理；
- 资产 taxonomy、目录布局、字段与存储方式；
- Canonical IR、Schema、CLI、适配器或其他具体实现架构；
- TUI 增强、强制 Hard Handoff、每次任务实时 Skill discovery、现场任意生成子 Agent 装配；
- 把 Work Type × Subject × Situation、BMad、OpenSpec、SpecKit 或某组 micro methods 当作系统本体。

Memory/RAG、模型参数、权限沙箱、Hooks、子 Agent 定义等也不属于当前核心资产；只有真实需求或 bad case 证明必要时再重新评估。

## 尚未决定

- 哪些稳定工作配置、变体和适用边界会从真实工作中形成，以及 Profile 最终只是激活入口、复用宏，还是承担更多产品语义；
- Soft Switch 何时足够，何时需要显式 clean-room / Hard Handoff；Hard Handoff 当前不是默认或强制规则；
- 新场景下何时启动 Skill discovery、允许投入多少成本以及何时停止；该问题已停放，不阻塞当前核心闭环；
- 如何评估并利用 BMad、SpecKit、Matt Skills 等现有方法包，以及如何治理自建或 fork 的 Skill 生命周期；
- 机械验证与低成本语义判断的具体分界，以及未来是否有真实案例要求加入 Instructions、Skills、MCP 之外的同层级核心资产。
